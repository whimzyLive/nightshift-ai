# Blogs on the Marketing Site — Technical Spec

**Story:** NA-84 — Add Blogs pages to Marketing site & Model
**Epic:** none (NA-84 has no parent — the story description is the sole product context)
**Date:** 2026-07-30

## Overview

Adds a `posts` Payload collection and a public `/blog` section (listing + detail) to
`apps/marketing`, so visitors can browse and read published posts. All post pages are pre-rendered
at build time and re-rendered on demand when an author changes a post in the Payload admin.

**Owning agent:** `web-engineer` (owns `apps/marketing/`, `packages/ui/`, `apps/marketing-e2e/`).
No other active agent is involved — the CMS, the DB migration, and the UI all live inside
`apps/marketing`, which `web-engineer` owns end to end.

## Data Model

### New collection — `posts`

File: `apps/marketing/src/collections/Posts.ts` (new). Config follows the schema agreed in the
story description; deviations are listed under [Decisions](#decisions-made-in-this-spec).

| Field                     | Payload type                     | Required | Default | Notes                                                                                     |
| ------------------------- | -------------------------------- | -------- | ------- | ----------------------------------------------------------------------------------------- |
| `title`                   | `text`                           | Yes      | —       | `admin.useAsTitle`                                                                          |
| `excerpt`                 | `textarea` (`maxLength: 300`)    | Yes      | —       | Listing card copy. Deliberately distinct from `meta.description` (AC3)                      |
| `heroImage`               | `upload` → `media`               | No       | —       | Rendered on the detail page only                                                            |
| `content`                 | `richText` (lexical)             | Yes      | —       | Features: root + `HeadingFeature(h1–h4)`, `BlocksFeature([Banner, Code, MediaBlock])`, fixed/inline toolbars, horizontal rule |
| `meta.title`              | `text` (plugin-seo field)        | No       | —       | Inside the `meta` tab/group; `hasGenerateFn: true`                                          |
| `meta.description`        | `textarea` (plugin-seo field)    | No       | —       | SEO description — **not** the listing excerpt                                               |
| `meta.image`              | `upload` → `media`               | No       | —       | OG image override                                                                           |
| `publishedAt`             | `date` (`dayAndTime`)            | No       | —       | Sidebar. Owns a **field-level** `hooks.beforeChange`, declared inline on this field in `Posts.ts` (not a collection-level hook): given `({ siblingData, value })`, return `new Date()` when `siblingData._status === 'published'` and `value` is empty, else return `value` unchanged. Load-bearing — `getBlogIndex()` sorts on `-publishedAt`, so a published post must never carry a null date |
| `authors`                 | `relationship` → `users`, hasMany| No       | —       | Sidebar. Not readable by the public API (see `populatedAuthors`)                             |
| `populatedAuthors`        | `array` of `{ id: text, name: text }` | No  | —       | `admin.disabled`, `readOnly`, `access.update: () => false`; filled by the `populateAuthors` `afterRead` hook. Load-bearing: `users` read access is locked, so the public API returns no author names from `authors` |
| `slug`                    | `text`, `unique`, `index`        | Yes (by hook) | —  | Derived from `title`; URL key for `/blog/[slug]` — see Decision D1                            |
| `_status`                 | `select` (`draft` \| `published`)| —        | `draft` | Added automatically by `versions.drafts`                                                     |

Collection-level config:

- `access`: `create`/`update`/`delete` → `authenticated`; `read` → `authenticatedOrPublished`.
- `versions`: `drafts: { autosave: { interval: 100 }, schedulePublish: true }`, `maxPerDoc: 50`.
- `defaultPopulate`: `{ title: true, slug: true, excerpt: true, meta: { image: true, description: true } }`.
- `admin`: `useAsTitle: 'title'`, `defaultColumns: ['title', 'slug', 'publishedAt', 'updatedAt']`,
  `group: 'Content'` (matches the existing `Faq` collection's admin grouping).
- `hooks`: `afterChange: [revalidatePost]`, `afterRead: [populateAuthors]`, `afterDelete: [revalidateDelete]`.
  `revalidatePost` and `revalidateDelete` are two distinct named exports of the same file
  (`hooks/revalidatePost.ts`) with different responsibilities — `afterDelete` receives no
  `previousDoc`, so the previous-slug purge exists only on `afterChange`. See the file table under
  [Backend Implementation](#backend-implementation-payload-layer-appsmarketing).
- There is **no** collection-level `beforeChange`: the only `beforeChange` in this collection is the
  field-level one on `publishedAt` above, and the only `beforeValidate` is the field-level one
  inside `slugField()`.

### Migration

The postgres adapter generates the DDL — the implementer runs `pnpm payload migrate:create` inside
`apps/marketing` and commits the emitted `.ts` + `.json` pair, then registers it in
`src/migrations/index.ts` (same shape as `20260712_054942_na31_faq_and_why_sdlc`).

Tables the migration is expected to create: `posts`, `posts_populated_authors`, `posts_rels`,
`_posts_v`, `_posts_v_version_populated_authors`, `_posts_v_rels`, `search`, `search_rels`, plus
`payload_jobs` (pulled in by `schedulePublish: true`) and the `enum__posts_v_version_status` /
`enum_posts_status` enums. **Do not hand-write the migration** — generate it, then read it back to
confirm nothing unexpected (e.g. a destructive change to `faq`/`media`) crept in.

### Permissions

The permission source is the collection `access` config in `apps/marketing/src/collections/*.ts`.
`Users` has **no `roles` field**, so exactly two principals exist in this project — do not invent
more.

| Principal                                                | posts: List             | posts: Get              | posts: Create | posts: Update | posts: Delete | search: Read | search: Write |
| -------------------------------------------------------- | ----------------------- | ----------------------- | ------------- | ------------- | ------------- | ------------ | ------------- |
| Public / unauthenticated visitor                          | ✓ published only        | ✓ published only        | ✗             | ✗             | ✗             | ✓            | ✗             |
| Authenticated Payload `users` doc (admin session **or** API key) | ✓ incl. drafts   | ✓ incl. drafts          | ✓             | ✓             | ✓             | ✓            | ✗ (hooks only)|

Access helpers (new, `apps/marketing/src/access/`):

```typescript
// apps/marketing/src/access/authenticated.ts
import type { Access } from 'payload';
export const authenticated: Access = ({ req: { user } }) => Boolean(user);

// apps/marketing/src/access/authenticatedOrPublished.ts
import type { Access } from 'payload';
export const authenticatedOrPublished: Access = ({ req: { user } }) => {
  if (user) return true;
  return { _status: { equals: 'published' } };
};
```

`searchOverrides.access` must be set to `{ read: () => true, create: () => false, update: () => false, delete: () => false }`.
The plugin's own sync hooks run with `overrideAccess`, so a locked-down index still stays in sync.

### Request / Response shapes

Public shapes the frontend depends on. All fields fully typed; the generated `Post` / `Search`
types from `src/payload-types.ts` are the upstream source.

```typescript
// apps/marketing/src/lib/blog.ts

import type { SerializedEditorState } from '@payloadcms/richtext-lexical/lexical';
import type { Media, Post, Search } from '../payload-types';

/**
 * One card on /blog — projected from a `search` index doc.
 *
 * `id` is derived from the generated type, following the `src/lib/faq.ts`
 * convention (`id: Faq['id']`). This app uses the postgres adapter, so every
 * generated collection id is `number`, never `string` — hardcoding `string`
 * here would break the `docs.map((doc) => ({ id: doc.id, ... }))` projection.
 * `Search` only exists in `payload-types.ts` once `payload generate:types` has
 * run with `searchPlugin` registered.
 */
export interface BlogIndexItem {
  id: Search['id'];
  slug: string;
  title: string;
  excerpt: string;
  /** ISO-8601 timestamp, or null when an author published without a date. */
  publishedAt: string | null;
}

/**
 * Author name resolved server-side from `populatedAuthors`.
 *
 * `id` is deliberately `string` here, unlike every other id in this file:
 * `populatedAuthors[].id` is an array-row `text` field holding a stringified
 * user id, not a generated collection primary key. Do not "correct" it to
 * `User['id']`.
 */
export interface BlogAuthor {
  id: string;
  name: string;
}

/** Everything /blog/[slug] renders. */
export interface BlogPostDetail {
  id: Post['id'];
  slug: string;
  title: string;
  excerpt: string;
  publishedAt: string | null;
  authors: BlogAuthor[];
  heroImage: Pick<Media, 'url' | 'alt' | 'width' | 'height'> | null;
  content: SerializedEditorState;
  meta: {
    title: string | null;
    description: string | null;
    imageUrl: string | null;
  };
}

export declare function getBlogIndex(): Promise<BlogIndexItem[]>;
export declare function getPublishedPostSlugs(): Promise<string[]>;
export declare function getPostBySlug(slug: string): Promise<BlogPostDetail | null>;
export type { Post };
```

```typescript
// apps/marketing/src/search/beforeSync.ts — shape of the synced index doc
import type { BeforeSync } from '@payloadcms/plugin-search/types';

export const beforeSyncWithSearch: BeforeSync = async ({ originalDoc, searchDoc }) => {
  const { id, slug, title, excerpt, publishedAt, meta } = originalDoc;
  return {
    ...searchDoc,
    slug,
    excerpt,
    publishedAt,
    meta: {
      ...meta,
      title: meta?.title || title,
      image: meta?.image?.id || meta?.image,
      description: meta?.description,
    },
  };
};
```

### Reader contract (`src/lib/blog.ts`)

Every reader repeats the established shape from `src/lib/faq.ts`:

1. `if (!isDbConfigured()) { warnDbNotConfiguredOnce(); return <empty>; }`
2. `const payload = await getPayload({ config });`
3. `return withDbFallback('[blog]', <empty>, async () => { ... });`

Query rules — **all three are required**:

| Reader                   | Collection | Query                                                                                                   |
| ------------------------ | ---------- | -------------------------------------------------------------------------------------------------------- |
| `getBlogIndex()`         | `search`   | `where: { 'doc.relationTo': { equals: 'posts' } }`, `sort: ['-publishedAt', '-createdAt']`, `limit: 500`, `depth: 0`, `overrideAccess: false`. The `-createdAt` tiebreaker keeps ordering deterministic for any index doc whose `publishedAt` is still null (only reachable for rows written before the `publishedAt` field hook existed) |
| `getPublishedPostSlugs()`| `posts`    | `where: { _status: { equals: 'published' } }`, `limit: 500`, `depth: 0`, `overrideAccess: false`, `draft: false`, **`context: { skipPopulateAuthors: true }`** — this reader consumes only `slug`, and the flag is what stops `populateAuthors` firing up to 500 `users` lookups per build (Decision D9) |
| `getPostBySlug(slug)`    | `posts`    | `where: { and: [{ slug: { equals: slug } }, { _status: { equals: 'published' } }] }`, `limit: 1`, `depth: 2`, `overrideAccess: false`, `draft: false` — returns `null` on no match |

> **This is the AC5 correction.** The story's schema note says AC5 "needs no bespoke filtering"
> because of `access.read: authenticatedOrPublished`. That is true for REST/GraphQL, but the
> frontend reads through the **Local API**, which defaults to `overrideAccess: true` and would
> therefore return drafts. Both `overrideAccess: false` **and** the explicit `_status` filter are
> mandatory — the filter is the assertion a test can pin, the flag is the defence in depth.

Reader results must be plain, serializable objects (`BlogIndexItem` / `BlogPostDetail`) — never raw
Payload docs — so the listing's client component receives serializable props.

- `generateStaticParams()` returns `(await getPublishedPostSlugs()).map((slug) => ({ slug }))` — every
  published post is pre-rendered at build.

  build renders on first request instead of 404ing.
- The `revalidatePost` hook re-renders `/blog` and the affected `/blog/<slug>` on every change.
- No client-side fetch is used to render post content on either route.

### Keyword search (AC3)

Server-side, at build: `/blog` calls `getBlogIndex()` once and passes `BlogIndexItem[]` to
`blog-index.tsx`. Client-side: a controlled `<input type="search">` filters that array
case-insensitively on `title` + `excerpt`, debounce-free (the list is small and already in memory).
No runtime fetch — which is what keeps AC2's "no client-side fetch" property intact while still
satisfying AC3. The input is labelled (`aria-label="Search blog posts"`), and the result count is
announced via `aria-live="polite"`.

### Data flow summary

```
/blog          → getBlogIndex()          → search collection (published-only index) → BlogIndexItem[] → <BlogIndex> (client filter)
/blog/[slug]   → getPostBySlug(slug)     → posts collection (published only)        → BlogPostDetail  → <PostHeader> + <PostBody>
generateStatic → getPublishedPostSlugs() → posts collection (published only)        → string[]
```

### SEO

- `blogMetadata` added to `src/lib/seo/metadata.ts` for `/blog` (canonical `/blog`, OG type
  `website`, reusing `seoSite.ogImageHome`).
- `/blog/[slug]` `generateMetadata()`: title `meta.title ?? title`, description
  `meta.description ?? excerpt`, canonical `/blog/<slug>`, OG type `article`, OG image
  `meta.image?.url ?? seoSite.ogImageHome`. Returns the base metadata unchanged when the post is
  missing (the page itself 404s).
- `src/lib/seo/jsonld.ts` gains `BlogPostingNode` + `buildBlogPostingNode(id, post)` (returns `null`
  for a missing post, matching `buildFaqPageNode`'s empty-input convention) and adds the node to the
  `JsonLdNode` union. `description` uses `excerpt` — the full Lexical body is **not** converted to
  plaintext for `articleBody`.

### Seed data

`src/seed/data.ts` + `src/seed/seed.ts` extend with a `postSeedData` array, upserted by `slug`
(the same idempotent find-then-update/create loop the `faq` seed already uses), each seeded doc
created with `_status: 'published'` and a `publishedAt`. Seed writes must pass
`context: { disableRevalidate: true }` so `revalidatePath` is not called outside a Next request
context (`payload run` would otherwise throw). Content: one launch post per existing site pillar
(why-SDLC, the team, the FAQ), with copy adapted by the implementer from the corresponding existing
page components — no new product claims are invented.

## Decisions made in this spec

Each item was left ambiguous or slightly inaccurate by the story's technical reference; each has a
concrete resolution so implementation can proceed without asking.

**D1 — `slug` field type.** The story writes `{ name: 'slug', type: 'slug', useAsSlug: 'title' }`.
Payload `3.85.2` core exposes **no `slug` field type**; the upstream website template implements it
as a helper. Resolution: add `src/fields/slug.ts` exporting `slugField()` → a `text` field with
`unique: true`, `index: true`, `admin.position: 'sidebar'`, and a `beforeValidate` hook that
lowercases the title, strips non-alphanumerics to `-`, and collapses repeats — applied only when the
slug is empty, so a hand-edited slug is never overwritten. _If_ `pnpm payload generate:types` proves
a core `slug` type exists in the installed version, prefer the core field and delete the helper.

**D2 — Keyword search mechanism.** `@payloadcms/plugin-search` is installed and syncs published
posts (per the story), but the listing does **not** query it at runtime: `/blog` reads the index once
at build and filters client-side in memory. Rejected alternative: a runtime `GET /api/search?...`
from the browser — it would add a client fetch to the listing for no benefit at this catalogue size
and would make the listing dynamic.

**D3 — `publishedAt` added to `beforeSync`.** AC3 requires the listing to show a publish date, and
the listing's only source is the search index. This is the same class of deviation the story already
documents for `excerpt`, and is justified identically.

**D4 — Rich-text blocks are in scope.** `Banner`, `Code`, and `MediaBlock` are in the agreed
`BlocksFeature` list and are not in the story's "deliberately omitted" set, so both their configs and
their frontend JSX converters ship in this story. Without the converters an authored block renders
as nothing, so they are not optional.

**D5 — `schedulePublish: true` is kept, its runner is not.** Enabling it adds the `payload_jobs`
collection to the schema. Scheduled publishes only fire when the jobs queue is actually run
(a cron hitting Payload's jobs-run endpoint). This story ships the flag and the schema; wiring the
Vercel cron is out of scope. Nothing breaks without it — drafts and immediate publishing work
normally, scheduled entries simply wait.

**D6 — Collection slug `posts`, URL prefix `/blog`.** The collection keeps the story's `posts` slug
(and therefore `/api/posts`), while the public routes use `/blog` to match the story's "Blogs
section" language. This mismatch is intentional; do not rename either side.

**D7 — Author display name.** `Users` has no `name` field and adding one is out of scope, so
`populateAuthors` writes `user.name ?? user.email` into `populatedAuthors[].name`. The detail page
renders those names verbatim and omits the byline entirely when the array is empty.

**D8 — `isActiveLink` gains a section-root prefix rule.** `Blog` is the first nav entry with child
routes. `isActiveLink` in `packages/ui/src/lib/nightshift/nav-bar.tsx` is currently an exact match,
so on `/blog/<slug>` the nav would render with no active item at all. Resolution — keep the existing
`/#`-anchor branch first, and widen only the final branch:

```typescript
export function isActiveLink(pathname: string, href: string): boolean {
  if (href.startsWith('/#')) return pathname === '/';
  return pathname === href || pathname.startsWith(`${href}/`);
}
```

The trailing slash in the prefix is required — without it `/blog-archive` would match `/blog`. This
is a behaviour change to shared UI, but a no-op for the four existing entries, all of which are leaf
routes with no children, so no existing active state moves. Both the desktop `<nav>` and
`MobileOverlay` call the same helper, so one change covers both surfaces. Rejected alternative: an
explicit `SECTION_ROOTS` allowlist — a second list to keep in sync with `NAV_LINKS` for no gain at
this size.

**D9 — `populateAuthors` is opt-out, not unconditional.** As a plain `afterRead` hook it fires on
every read of every post, including `getPublishedPostSlugs()` (`limit: 500`, `depth: 0`), which
consumes nothing but `slug` — up to 500 wasted `users` lookups per build. Resolution: keep the hook
on `afterRead` (it must stay read-time so an author rename shows up without re-saving every post),
but give it two early-return guards — `req.context.skipPopulateAuthors === true`, and an
absent/empty `authors` array — and have `getPublishedPostSlugs()` pass that context flag. Rejected
alternative: denormalising at write time via `afterChange` — it costs a second write per save,
interacts badly with autosave drafts, and leaves `populatedAuthors` stale after a user rename.
`getPostBySlug()` deliberately does **not** set the flag; it is the one reader that needs the byline.
