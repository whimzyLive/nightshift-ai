# Blogs pages on the Marketing site & Model — Technical Spec

**Story:** NA-82 — Add Blogs pages to Marketing site & Model
**Epic:** NA-20 — Marketing Site Hosting & Deployment (no description, no comments — story description is the sole product context)
**Feature:** none — no `docs/features/*.md` exists for NA-20
**Date:** 2026-08-01

## Overview

Adds a `posts` Payload CMS collection to `apps/marketing` plus a public `/blog` listing and `/blog/[slug]` detail route, both statically pre-rendered at build. Keyword search over published posts is backed by the Payload search plugin index.

## Data Model

**Base type:** `CollectionConfig` from `payload`, registered in the `collections` array of `src/payload.config.ts` — identical to the existing `Faq`, `Media`, `Users`. This project has no ORM entity base class; Payload collections are the persistence model and `@payloadcms/db-postgres` derives the Postgres tables. `id` is `number` (serial) — the adapter default, no `idType` override in this config.

## API Surface

No hand-written Next.js route handlers are added. Every endpoint below is auto-generated by Payload for the new collections and served through the existing catch-all at `src/app/(payload)/api/[...slug]/route.ts`.

### New Endpoints

| Method | Path | Auth/Route Type | Description |
| --- | --- | --- | --- |
| GET | /api/posts | public, no auth — `read: authenticatedOrPublished` filters to `_status: published` for anonymous callers | List posts |
| GET | /api/posts/:id | public, no auth — same filter | Get one post by id |
| POST | /api/posts | authenticated (session cookie or `users` API key) | Create post |
| PATCH | /api/posts/:id | authenticated | Update post |
| DELETE | /api/posts/:id | authenticated | Delete post |
| GET | /api/search | public, no auth — `read: () => true` on the search collection | Keyword query over the synced index; drives AC3 |
| POST/PATCH/DELETE | /api/search* | authenticated, and never called by this feature — the index is written only by the plugin's own sync hooks | Index mutation |

The frontend's build-time reads use the **Payload Local API** (`getPayload({ config })`), not these HTTP endpoints — matching `src/lib/faq.ts`. The only runtime HTTP call this feature makes is the browser's `GET /api/search` when a visitor types a query.

### Permissions

This project has **no role model**. `src/collections/Users.ts` declares no `roles` field, and access is decided purely by presence of `req.user` (session cookie or `useAPIKey` API key). The two principals below are the complete, actual set — derived from the collection `access` functions and `Users.auth`, not invented.

| Principal | List posts | Get post | Create | Update | Delete | Search index |
| --- | --- | --- | --- | --- | --- | --- |
| anonymous (site visitor) | ✓ published only | ✓ published only | ✗ | ✗ | ✗ | ✓ read only |
| authenticated user / API-key holder | ✓ incl. drafts | ✓ incl. drafts | ✓ | ✓ | ✓ | ✓ read; writes only via plugin hooks |

`authenticatedOrPublished` is what makes row 1 safe: it returns `true` for authenticated callers and otherwise narrows the query to `_status: { equals: 'published' }`. That single access function satisfies AC5 on both routes — no bespoke draft filtering anywhere in the page or data layer.

## Web UI

**Pages:**
| Route | File | Rendering | Description |
| --- | --- | --- | --- |
| /blog | `src/app/(frontend)/blog/page.tsx` | Static (async Server Component, build-time Local API read) | Listing: all published posts + keyword search |
| /blog/[slug] | `src/app/(frontend)/blog/[slug]/page.tsx` | Static via `generateStaticParams()` | Detail: full lexical content |

Static-rendering contract (AC2):

- `/blog/[slug]` exports `generateStaticParams()` returning every published post's slug — all published posts are pre-rendered at build.
- `dynamicParams = true` (Next.js default; state it explicitly). A post published *after* the build renders on first request and is then cached — with `dynamicParams = false` `revalidatePath` could never materialise a page that did not exist at build time. AC5 is still upheld because a draft's slug returns nothing under `authenticatedOrPublished`, and the page calls `notFound()`.
- `revalidatePost` / `revalidateDelete` give on-demand re-render on publish/edit/delete. No time-based `revalidate` value is set.
- Neither route fetches post content from the client. The only client fetch in this feature is search (AC3), which is navigation, not content.
- `generateMetadata()` on the detail route builds `Metadata` from `meta.title || title`, `meta.description || excerpt`, `meta.image || heroImage`, with `alternates.canonical: '/blog/' + slug` resolving against the layout's `metadataBase`.
- Both routes follow the established single-async-boundary rule (see `faq/page.tsx`): exactly one async Server Component at the top; every section below is synchronous and receives resolved data. A second nested async Server Component breaks RTL `render()`.

**Data hooks / server data layer — `src/lib/posts.ts`**, following `src/lib/faq.ts` exactly (`isDbConfigured()` short-circuit → `getPayload({ config })` → `withDbFallback(tag, fallback, op)`; a connection/init error rethrows so a DB outage fails the build, a row-level defect degrades to the fallback):

| Function | Returns | Used by |
| --- | --- | --- |
| `getPublishedPosts()` | `Promise<BlogListItem[]>` — `sort: '-publishedAt'`, `limit: 200`, `depth: 1` | `/blog` |
| `getPostSlugs()` | `Promise<string[]>` — `depth: 0`, slug only | `generateStaticParams()` |
| `getPostBySlug(slug: string)` | `Promise<BlogPostDetail \| null>` — `where: { slug: { equals: slug } }`, `limit: 1`, `depth: 2` | `/blog/[slug]` page + `generateMetadata` |

Log tag `'[posts]'`. Fallbacks: `[]`, `[]`, `null`.

**State:** no global client store exists in this app and none is added. Search query, results, and loading state are local `useState` inside `post-list.tsx` / `blog-search.tsx`.

**Search behaviour (AC3)** — the ticket mandates `searchPlugin`, and its note that `beforeSync` must carry `excerpt` only makes sense if the query hits the index. Therefore: empty query → render the statically pre-rendered `BlogListItem[]` (zero network). Non-empty query → debounced `GET /api/search?depth=0&limit=20&where[or][0][title][like]=<q>&where[or][1][excerpt][like]=<q>`, results rendered as the same `post-card`. Failure or offline → keep the pre-rendered list visible and show an inline "search unavailable" notice; never blank the page. See OQ1 for the no-plugin alternative.

**Route permissions:** this app has no route-permission config — every `(frontend)` route is public. `/blog` and `/blog/[slug]` are public; draft exclusion is enforced at the collection access layer, not the route.

**SEO:** `blogMetadata` for `/blog`; per-post `generateMetadata` for the detail route; a `BlogPosting` JSON-LD node emitted through the existing `JsonLd` component on the detail page, built by a new `buildBlogPostingNode(...)` in `lib/seo/jsonld.ts`. Absolute URLs resolve from `seoSite.siteUrl`.

## Error Handling

| Scenario | Behaviour | HTTP Status |
| --- | --- | --- |
| `/blog/[slug]` slug not found, or slug belongs to a draft | `notFound()` → Next.js 404 page | 404 |
| No published posts exist at build | `/blog` renders `blog-empty-state` (no-posts variant); build succeeds | 200 |
| `DATABASE_URL` unset (e.g. CI build without secrets) | `isDbConfigured()` short-circuits; readers return `[]` / `null`; `generateStaticParams()` returns `[]`; build succeeds with an empty blog | 200 |
| DB connection/init failure during build | `withDbFallback` rethrows via `isConnectionOrInitError` — build fails loudly | build error |
| Row-level query defect (bad row, mapper throw) | Logged under `[posts]`, degraded to `[]` / `null` | 200 |
| `GET /api/search` fails, times out, or the visitor is offline | Client keeps the pre-rendered list rendered and shows an inline non-blocking notice | n/a (client-side) |
| Search returns zero hits | `blog-empty-state` (no-results variant) with a clear-search affordance | 200 |
| Anonymous `POST/PATCH/DELETE /api/posts` | Payload access denial | 403 |
| Create/update a post with a slug that already exists | Payload unique-index violation surfaced as an admin field error | 400 |
| `excerpt` missing or > 300 chars | Payload validation error in admin | 400 |
| `content` empty | Payload `required` validation error in admin | 400 |
| Post published with no `publishedAt` | `beforeChange` field hook stamps `new Date()` — never an error | 200 |
| Post has `authors` but none resolvable | `populatedAuthors` empty; byline omitted entirely, no "undefined" text | 200 |
| `heroImage` missing | Card and header render text-only; layout must not reserve a broken image box | 200 |

**Offline behaviour:** N/A — no offline writes. The site is read-only to visitors.

## Out of Scope

Verbatim from the story, plus the boundaries this spec adds:

- Comments, likes, or social sharing on blog posts.
- Custom authoring UI beyond Payload's built-in admin panel.
- Tagging/category taxonomy and related-posts recommendations — hence **no** `categories` relationship, **no** `Categories` collection, **no** `relatedPosts` field, **no** `RelatedPosts` block, **no** `nestedDocsPlugin`, and **no** category-population loop in `beforeSync`.
- RSS feed generation.

Added by this spec:

- Pagination on `/blog` — the `limit: 200` read is sufficient at current volume.
- A `roles` field on `users` — the binary anonymous/authenticated model stands.
- A Payload storage adapter for `media` (see OQ3).
- Live preview / draft-preview routes for editors.
- Author profile pages.
- Sitemap and RSS entries for posts.
- Changing `Faq`/`Media` access or any existing route.

## Open Questions

- [ ] **OQ1 — Is a runtime `/api/search` call acceptable on the marketing site?** It adds a runtime DB dependency to an otherwise fully static site. Suggested default: **yes, keep `searchPlugin`** — the ticket mandates it and its `excerpt`-in-`beforeSync` note presumes an index query. Fallback if Tech Lead rejects the runtime dependency: drop both the plugin and the `search` collection and filter the pre-rendered `BlogListItem[]` client-side on `title` + `excerpt`; AC3 still passes and the site stays zero-network.
- [ ] **OQ2 — Ship all three lexical blocks (Banner, Code, MediaBlock) in this story?** Each needs a config plus a frontend renderer, which is real weight in an 8-point story. Suggested default: **yes, all three** — the ticket's schema mandates them, and any block an editor can insert must render. Reduce to `Code` + `MediaBlock` only if the story overruns; if so, remove `Banner` from `BlocksFeature` in the same change so no unrenderable block is ever insertable.
- [ ] **OQ3 — `media` has no storage adapter** (`upload: true`, local disk), so `heroImage` and `meta.image` uploads do not survive a Vercel deploy. Suggested default: **leave it** — `heroImage` is optional and this predates NA-82; file a follow-up story for a storage adapter rather than widening this one.
- [ ] **OQ4 — NA-82 has no `parent` set in Jira** (`fields.parent` is `null`); the NA-20 linkage came from the dispatch, and NA-20 itself has no description and no comments. Suggested default: **proceed** — the story description is self-contained product context; set the parent link on NA-82 as housekeeping.
- [ ] **OQ5 — `users.name` optional vs required.** Required would break `payload migrate` against an existing non-empty `users` table. Suggested default: **optional**, with the byline omitted when absent (see Error Handling).
