## Overview

Agent rule writes and QA review-round records stop landing as committed files on the story branch and are instead captured to a gitignored staging area in the primary checkout. A memory file enters a PR only when a human promotes a captured item through `/sdlc:docs distill`.

## Data Model

This project has no database. "Entities" here are on-disk artifacts with YAML frontmatter — the same class the existing rule/review schemas define.

### New Entities

**Capture record — rule kind.** Path `<primary-checkout>/.claude/memories/captured/rules/<STORY-KEY>--<rule-id>.md`.

| Field | Type | Nullable | Default | Notes |
| --- | --- | --- | --- | --- |
| id | string | No | — | kebab-case rule id; equals the `<rule-id>` filename segment |
| agent | string[] | No | — | the **promote-target** agent(s), never the capturing agent: exactly `[<owning-agent>]` when `promote-target` is under that agent's dir, length >= 2 under `shared/`. `check-frontmatter.sh:171` enforces `agent == dirname` on the promoted file, so the capture must already carry the target's name (a QA-authored capture for `web-engineer` carries `agent: [web-engineer]`) |
| trigger | string[] | No | — | 1-6 lowercase keyword phrases |
| rule | string | No | — | ONE line, <= 200 chars |
| evidence | string[] | No | — | length >= 1; Jira key \| `PR#n` \| 7-40 char SHA |
| uses | number | No | 0 | applications recorded **by this capture**: `0` for a first-authorship capture, `>= 1` for a counter-only capture. Promotion adds it to the target's existing count — see Decision D2 |
| status | `"captured"` | No | `captured` | capture-only status; never `active`, so `collect-memory.sh` cannot pick it up |
| captured | string | No | — | ISO-8601 UTC timestamp of the capture write |
| story | string | No | — | originating Jira key, e.g. `NA-98` |
| origin | `"domain-agent"` \| `"qa-round"` | No | — | which write path produced it — i.e. **who wrote it**, as distinct from `agent`, which is who it will bind |
| promote-target | string | No | — | repo-relative path this record becomes on promotion, e.g. `.claude/memories/agents/web-engineer/<rule-id>.md` |

**Capture record — review kind.** Path `<primary-checkout>/.claude/memories/captured/reviews/<YYYY-MM-DD>-<STORY-KEY>[-rN].md`.

| Field | Type | Nullable | Default | Notes |
| --- | --- | --- | --- | --- |
| story | string | No | — | Jira key; must match the filename segment. Already part of the committed 5-field review schema — not a capture-only field |
| date | string | No | — | `YYYY-MM-DD`; must match the filename segment |
| domains | string[] | No | — | agents this round touched; `[]` only when `issue_count` is 0 |
| root_causes | string[] | No | — | tokens from `${CLAUDE_PLUGIN_ROOT}/refs/root-cause-vocab.txt`; `[]` only when `issue_count` is 0 |
| issue_count | number | No | — | count of Critical + Important findings this round |
| captured | string | No | — | ISO-8601 UTC timestamp |
| origin | `"qa-round"` | No | `qa-round` | fixed for this kind |
| promote-target | string | No | — | `.claude/memories/reviews/<YYYY-MM-DD>-<STORY-KEY>[-rN].md` |

Body of a review capture is unchanged from today's round file: `## Issues` / `## Preventions` / `## Rules written` when `issue_count > 0`; frontmatter only when `issue_count: 0`.

**Staging-area ignore marker.** `.claude/memories/captured/.gitignore`, content exactly:

```gitignore
*
!.gitignore
```

Self-ignoring so the staging area is invisible to git in **every** consumer repo without editing that repo's root `.gitignore` — the plugin is public and must not depend on nightshift's root ignore file. This is the mechanism that satisfies AC3 and AC6.

Entity base class: N/A — no ORM in this project. The frontmatter base is the existing 7-field rule schema (`refs/domain-agent-handoff.md`) and the existing 5-field review schema (`refs/qa-engineer-playbook.md` Step 5). The rule kind gains **four** capture-only fields (`captured`, `story`, `origin`, `promote-target`); the review kind gains **three** (`captured`, `origin`, `promote-target`) because `story` is already in its committed schema. Nothing else is added to either. Promotion is therefore a bounded, mechanical transform — strip the capture-only fields, set `status: active` (rule kind only), rename `<STORY-KEY>--<rule-id>.md` → `<rule-id>.md`, merge `uses`/`evidence` into an existing target if one exists (Decision D2), and write to `promote-target` — never a schema reshape and never a re-authoring of the `rule` line.

## API Surface

No HTTP surface. The callable contracts are two shell scripts and one MCP tool call.

### New Endpoints

| Method | Path | Auth/Route Type | Description |
| --- | --- | --- | --- |
| exec | `plugins/sdlc/scripts/capture-learning.sh rule <agent-or-shared>/<rule-id> <STORY-KEY> [<body-file>\|-]` | agent-local shell, no network | Write/overwrite one rule capture; prints `CAPTURED=<path>` |
| exec | `plugins/sdlc/scripts/capture-learning.sh review <STORY-KEY> <YYYY-MM-DD> <round> [<body-file>\|-]` | agent-local shell, no network | Write/overwrite one review capture; prints `CAPTURED=<path>` |
| exec | `plugins/sdlc/scripts/list-captured.sh [--json] [--story <STORY-KEY>] [--kind rule\|review] [--agent <agent-name>]` | agent-local shell, no network | Enumerate the capture corpus for distill and for in-story re-dispatch |
| MCP | `ctx_index({ path, source })` | context-mode MCP, session-scoped | `knowledge-engineer` only, at distill time — index the corpus it is about to cluster |

`<body-file>` is optional and also accepts the literal `-`: the committed rule schema states "Body is optional" (`domain-agent-handoff.md:90`), so a frontmatter-only capture is legal. Omitted or `-` both write frontmatter only. Neither form reads stdin — the script stays stdin-free so it composes inside an agent Bash block.

`--agent` filters rule captures on the `agent` list; it is what a re-dispatched domain agent uses to read this story's staged rules (Decision D8).

Both scripts read one environment variable, `SDLC_CAPTURE_ROOT` (Decision D3). It is **not** a project-context token and **not** scaffolded by `init.md` — deliberately: its only two callers are the test fixture, which points the scripts at a throwaway staging root, and a human doing manual recovery. Its home is this script contract; no consumer repo is expected to set it.

`ctx_index` is only callable where MCP tools exist. Every SDLC domain agent declares `tools: Read, Write, Edit, Bash, Skill` — **no MCP** — so a domain agent can never call it. The only consumer with a live use is `knowledge-engineer`: it indexes the corpus at the start of a distill run and `ctx_search`es it in the same session while clustering. That is why its `tools:` line widens. No indexing happens in the impl or QA phases — see Decision D7.

`summary` = the `rule` line for a rule capture; `"<issue_count> findings — <root_causes joined>"` for a review capture. `agents` = `agent` for a rule capture, `domains` for a review capture. **Durability constraint (why the file is the record).** context-mode's content and session stores are SQLite databases at `join(tmpdir(), "<prefix>-<pid>.db")` — per-process and ephemeral (verified in `src/db-base.ts` `defaultDBPath` at 1.0.103). Anything only inside `ctx_index` dies with the session, so a later `/sdlc:docs distill` run could never read it. The gitignored staging file is therefore the source of truth and `ctx_index` is a same-session read accelerator for the one agent that reads the corpus in the session that indexed it.

**Data-loss exposure (accepted, stated).** The staging area is untracked and ignored, so it has no git-history safety net — the mechanism this story removes. Verified: `git clean -ndx` reports `Would remove .claude/memories/captured/rules/` and `.../reviews/`, and `git worktree remove --force` deletes ignored files. Decision D3 removes the worktree-removal path; `git clean -x`/`-ndx` remains a real destructor and is accepted: a capture is a re-derivable nomination, not a deliverable, and the underlying evidence (Jira key, PR thread, SHA) survives in its own systems. Nothing in this story should be designed as if a capture were durable storage.

**`/sdlc:docs distill` integration (AC4).** Phase 1 gains the capture corpus as an evidence source alongside the maintenance-op nomination list. For each capture the founder gate presents `kind`, `id`/`story`, `summary`, and `promote-target`, and takes one of three per-item choices: `memory`, `adr`, or `skip` (leave it staged). Phase 2 executes the confirmed set as **two dispatches on one docs branch, one PR** — see Decision D1.

## Decisions

These were open questions in the first draft. All are decided here; the implementer has no judgement call left on any of them.

**D1 — Promotion ownership: the memory write belongs to `ai-enablement-engineer`, never `knowledge-engineer`.**
`adr-pipeline.md` §8 states verbatim that "`knowledge-engineer`'s phase-2 write touches only `docs/adr/**`, never `.claude/memories/**`", and `analyze-protocol.md:232` refuses any cross-agent memory write outside the two named exceptions. Distill's phase 2 therefore splits at the command layer: `knowledge-engineer` writes `docs/adr/**` for every `adr` choice; `ai-enablement-engineer` runs the new **capture-promotion** maintenance operation for every `memory` choice — writing `promote-target`, merging per D2, and deleting the promoted capture. Both dispatches commit to the same distill branch, so the founder still gets one PR from one interaction and AC4's per-item choice stays a single gate. This does not overturn §8. It does require Exception 2 to be widened in three places, not one — its op list, its action verbs and precondition (creating or merging into a rule file, gated on the distill gate's per-item `memory` choice rather than on a superseding ADR), and the two no-gate carve-outs whose targets this story moves — all itemised in the `analyze-protocol.md` Modified Entities row.

**D2 — `uses` advances at promotion, and the GC heuristic stops firing on staged counters.**
A capture's `uses` counts applications recorded by that capture (`0` first-authorship, `>= 1` counter-only). Promoting onto an existing target sets `uses := existing.uses + capture.uses` and unions `evidence`; promoting to a new path writes the capture's value as-is. The maintenance run order becomes capture promotion → decay/demotion → review-file GC → nomination → T1 deletion. Capture promotion is founder-gated *through distill's* gate and nomination *feeds* distill, so the two never close a loop inside one invocation: nomination reads counters that are current as of the last completed distill run, which means the single-agent promotion path keeps working with a lag of at most one distill cycle rather than dying. `analyze-protocol.md`'s `memory-gc-overdue` finding gains one clause: an `active` rule with `uses: 0` is **not** GC-eligible while an unpromoted rule capture with the same `id` exists, so a heavily-applied rule cannot be garbage-collected because its evidence is staged rather than committed.

**D3 — Captures always land in the primary checkout, resolved from `git worktree list --porcelain`.**
QA Step 5 runs entirely in `$WORKTREE` ("never the primary checkout"), and `worktree-gc.sh:135` runs `git worktree remove --force`, which deletes untracked **and ignored** files. Writing captures under `$WORKTREE` would destroy every QA-origin capture before any later distill run, failing AC4 outright. `capture-learning.sh` and `list-captured.sh` therefore resolve the staging root as:

```text
SDLC_CAPTURE_ROOT (if set and non-empty) -> use it verbatim
else first `worktree ` line of `git worktree list --porcelain` -> <main-worktree>/.claude/memories/captured
if that entry carries a `bare` line, or the command fails -> exit 1 with the reason; write nothing
```

The main worktree is always the first entry of `git worktree list --porcelain`, and that entry is correct under `--separate-git-dir`. `git rev-parse --path-format=absolute --git-common-dir` is **not** usable here: it returns the `.git` directory, not the worktree root, and its parent is not the worktree root under `--separate-git-dir`. Fail closed on a bare main repo rather than silently capturing into a linked worktree that `worktree-gc.sh` will delete.

`SDLC_CAPTURE_ROOT` is a script-level escape hatch for the test fixture and manual recovery only — no project-context token, no `init.md` scaffold (see the API Surface note).

**rtk note for the implementer.** This repo's rtk hook compacts `git worktree list --porcelain`, stripping the `worktree ` line prefix entirely. A parser exercised under the hook will appear to fail on well-formed output. Invoke the command through `rtk proxy` (or unhooked) when writing or debugging this parser and its test — the failure is in the observation path, not the parse.

**D4 — Retention reuses the existing `Review retention window` token; no new project-context token.**
The `ai-enablement-engineer` maintenance op's review-file GC sweeps captures older than that window (`6 months` here) under the same founder gate that governs every other GC deletion. "Unpromoted" and "stale" are indistinguishable from the outside, which is exactly why the sweep is founder-gated and never automatic — and why the exposure above is stated rather than engineered around.

**D5 — The QA Step-8 `Learnings:` line stays mandatory**, reworded to `captured to <N> file(s): <ids>`. Its purpose is the human-readable verdict record and the round-N+1 re-dispatch hint, not an indexing instruction (indexing moved to distill under D7).

**D6 — `/sdlc:analyze`'s `story-merged-without-review-entry` accepts a captured round file.**
It reports only when neither a committed round file nor a capture exists for the merged key; otherwise it goes permanently noisy the day round files stop being committed.

**D7 — context-mode integration is scoped to `knowledge-engineer` at distill time only.**
The impl/QA-phase `ctx_index` call from the first draft is deleted: domain agents have no MCP so they cannot `ctx_search` what was indexed, and the store dies with the session so a later distill cannot read it either. The only consumer that indexes and searches in the same session is `knowledge-engineer`, which is what justifies its `tools:` widening.

**D8 — The in-story learning loop is preserved by a script read, not by the index.**
`collect-memory.sh` surfaces `status: active` rules only, and captures are deliberately not collected — so without this, a rule captured in QA round 1 would be invisible to the fresh agent dispatched in round 2, degrading exactly the "QA rounds per story must not increase" gate. `refs/domain-agent-handoff.md`'s collection step therefore gains a second command run alongside `collect-memory.sh`:
`bash ${CLAUDE_PLUGIN_ROOT}/scripts/list-captured.sh --story <STORY-KEY> --kind rule --agent <your-agent-name>`
The agent reads the returned paths itself. Paths are handed over, never pasted rule text — prompt text amplifies far more than an on-demand Read.

- `ai-enablement-engineer` may write every path in this spec **except** `.github/workflows/ci.yml` — that file is `platform-engineer`-owned per the project-context table, and the standing rule `ci-yml-outside-ai-enablement-write-scope-refuse` requires a refusal rather than a courtesy edit. The two CI steps (one per new test file) are a separate platform-engineer task in the same story.
- `knowledge-engineer` gains **read** access to `.claude/memories/captured/**` and no write access to it or to `.claude/memories/**` at all. Its distill dispatch writes `docs/adr/**` only, unchanged from `adr-pipeline.md` §8.
- The capture-promotion op's write into another agent's rule directory is a cross-agent memory write, sanctioned only as the widened Exception 2: founder-confirmed, one specific promotion at a time, applied as a reviewable diff/PR. An unconfirmed promotion is the same violation class as a silent memory write today.
- The staging area is untracked, so nothing in it is subject to the review gate — which is exactly why nothing in it may reach a committed path without the gate.
