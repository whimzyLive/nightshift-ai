# Diagnose and fix RTK hook — Technical Spec

**Story:** NA-89 (Epic NA-76, workstream D)
**Feature:** docs/features/2026-07-30-sdlc-token-cost-optimisation-programme.md
**Date:** 2026-07-31

## Overview

The RTK `PreToolUse` hook is firing, but its rewrite engine only ever inspects the **first line** of a Bash command string, so 71.8% of achievable rewrites are lost on this repo's overwhelmingly multi-line command traffic. This story records that diagnosis on NA-76 and adds a repo-owned line-scanning wrapper that delegates eligibility to the upstream engine unchanged.

## Diagnosis

### What the Epic asserted vs what is true

NA-76 sized workstream D from "measured adoption 3.1% (89 rtk vs 2,758 raw) — the hook is not firing". Both halves of that sentence are wrong, in opposite directions, and the two errors must be separated before any fix is specified.

| # | Finding | Confidence | Basis |
| --- | --- | --- | --- |
| F1 | The 3.1% figure is a **measurement artifact**. Claude Code records the model-authored `tool_use.input.command` in the transcript, never the hook's `updatedInput`. A transcript-derived counter is therefore structurally incapable of seeing a hook rewrite — it can only ever count commands the model itself wrote as `rtk ...`. | High | Two independent confirmations, below |
| F2 | The hook **is** firing and the harness **does** apply `updatedInput`, with no `permissionDecision` field required. | High | Live end-to-end execution, below |
| F3 | A **real defect exists**: the rewrite engine considers only the first line of the command string. Lines 2..n are never examined. | High | Deterministic reproduction, below |
| F4 | F3 is **not fixed upstream**. rtk 0.42.0 (installed) and 0.44.1 (current stable) behave identically. | High | Side-by-side bottle comparison |
| F5 | The Epic's **2.3%-of-spend sizing for D is not established** and must be re-derived. It assumed 96.9% of eligible calls passed through raw; the true loss is 71.8% of achievable rewrites over a different and smaller eligible base, and the token value of those rewrites is unmeasured. | Medium — the loss is measured, its dollar value is not | See Non-findings |

### Evidence — F1 and F2 (measurement artifact)

Controlled live test, this repo, 2026-07-31. A bare `ls -la <dir>` was issued as a sole Bash tool call:

| Observation | Value |
| --- | --- |
| Command recorded in transcript | `ls -la <dir>` (raw — no `rtk` prefix) |
| Output actually returned | rtk-compressed form (`name  71B`, dirs suffixed `/`, no mode/owner columns) — not `ls -la` output |
| `rtk gain` "Total commands" before | 33542 |
| `rtk gain` "Total commands" after | 33543 |

The counter is internal to the upstream binary and increments only on real rtk execution. The rewrite happened; the transcript shows the pre-hook string. Corroborated across a 12-transcript corpus: 4 of 805 Bash calls (0.5%) are recorded as `rtk ...`, while replaying the same 805 strings through the live hook shows 265 (32.9%) receive a rewrite.

### Evidence — F3 (the actual defect)

Reproduction is deterministic. `rtk hook check <cmd>` is the upstream dry-run oracle; identical results via the real `rtk hook claude` stdin contract.

| Input | Output | Reading |
| --- | --- | --- |
| `git status; git log --oneline -3; grep -n x y.md` | `rtk git status; rtk git log --oneline -3; rtk grep -n x y.md` | Multiple rewrites **within one line** work correctly |
| `git status\ngit log --oneline -3` | `rtk git status\ngit log --oneline -3` | Line 2 never examined |
| `echo hi\ngit status` | *(no rewrite emitted at all)* | Line 1 ineligible -> **entire call** passes through |
| `export X=1\ngit status\ngrep -n a b.md` | *(no rewrite emitted at all)* | Same — a variable assignment on line 1 disables the hook for the whole call |

The third and fourth rows are the severe case: a leading `cd`, `export` or comment line silently disables rewriting for every command in the block. This repo's SDLC traffic opens with such a line constantly — `cd /Users/.../nightshift` is the single most frequent passthrough head (153 of 805 calls).

### Evidence — F4 (not fixed upstream)

rtk is a third-party Homebrew formula (`github.com/rtk-ai/rtk`, Apache-2.0), not vendored here. The 0.44.1 bottle was fetched without disturbing the linked 0.42.0 install and probed side by side.

| Case | 0.42.0 | 0.44.1 |
| --- | --- | --- |
| `git fetch origin --quiet\ngit status` | `rtk git fetch origin --quiet\ngit status` | identical |
| `cd /repo && git log --oneline -5\ngrep -n foo bar.md\ncat README.md` | only `git log` rewritten | identical |
| `acli jira workitem view NA-89 --json` | no rewrite | identical |

Upgrading rtk does not fix this. The limitation is stable across two minor releases.

### Measured loss

Corpus: the 12 most recently modified Claude Code transcripts for this project, 2026-07-31 — real `/sdlc:*` traffic, not authored for this story. Oracle: upstream `rtk hook check`, per line. Units are **rewrite occurrences**, not commands.

| Metric | Value |
| --- | --- |
| Bash tool calls | 805 |
| Single-line / multi-line | 280 (34.8%) / 525 (65.2%) |
| Calls containing a heredoc | 166 (20.6%) |
| Rewrites performed today | 234 |
| Rewrites achievable if every line were scanned | 830 |
| **Lost to the first-line defect** | **596 (71.8% of achievable)** |
| Calls losing >= 1 rewrite | 246 (30.6% of all calls) |

Top lost heads beyond line 1: `git fetch` 39, `git log` 33, `git show` 29, `git -C` 24, `grep -n` 23, `git add` 23, `gh pr` 20, `git worktree` 14. A second, independently written pass over the same corpus (top-level segment split, `&&` and newline) reported 352 of 702 eligible segments missed (50.1%) — same direction, different units and a coarser splitter. The two passes disagree by method, not by conclusion; the 596/830 figure is the one the gate below uses, because it models the defect exactly.

## The ADR 0015 hazard — binding constraint on D2

ADR 0015 (accepted; source stories NA-57, NA-62, NA-63) records that `rtk`-wrapped commands can print success while exiting non-zero, and that the standing remedy is to reach for the raw binary. Probing the two commands that ADR names:

| Command | Current hook behaviour |
| --- | --- |
| `pnpm exec tsc --noEmit` | rewritten to `rtk tsc --noEmit` |
| `pnpm exec prettier --check foo.md` | rewritten to `rtk prettier --check foo.md` |
| `pnpm nx run-many -t test` | no rewrite |

Widening coverage to lines 2..n **increases** exposure to a known-defective wrapper on exactly the commands whose exit code gates merges. D5 is therefore not optional hardening — it is a precondition of D2. Rationale: a token saving that silently converts a failing typecheck into a passing one costs more than it saves, which is the Epic's own stated stop condition.

### Request / Response Shapes

The wrapper consumes and produces the harness's existing hook contract; it introduces no new fields.

```typescript
// stdin — Claude Code PreToolUse payload (subset the wrapper reads)
interface PreToolUsePayload {
  session_id: string;
  transcript_path: string;
  cwd: string;
  hook_event_name: "PreToolUse";
  tool_name: string; // wrapper acts only when this is exactly "Bash"
  tool_input: BashToolInput;
}

interface BashToolInput {
  command: string;
  description?: string;
  timeout?: number;
  run_in_background?: boolean;
}

// stdout — emitted ONLY when at least one line was rewritten; otherwise emit nothing and exit 0
interface PreToolUseHookOutput {
  hookSpecificOutput: {
    hookEventName: "PreToolUse";
    permissionDecision: "allow";
    permissionDecisionReason: string; // "RTK line-scan rewrite"
    updatedInput: BashToolInput; // command replaced; all other fields copied verbatim
  };
}
```

`permissionDecision: "allow"` is emitted on every rewrite. Rationale: the upstream engine emits it inconsistently (present on some multi-line paths, absent on single-line ones) and the harness was observed to honour `updatedInput` without it — emitting it always removes the dependency on undocumented harness leniency.

Delegated eligibility contract, verbatim — the wrapper must not reimplement matching:

```text
# notation: plugins/sdlc/refs/pseudocode-notation.md  (:=, ->, ⊆, ASSERT/ELSE, first-match-wins)
verdict := rtk hook check "<line>"
exit 0 -> stdout is the rewritten line      # take it
exit 1 -> stdout is "No rewrite for: ..."   # discard, keep the raw line
```

## Backend Implementation

**Hook script — `.claude/hooks/rtk-line-scan.sh` (new, ai-enablement-engineer).** Reads the payload on stdin, and for a `Bash` tool call splits `tool_input.command` on newlines only, submits each line to `rtk hook check`, reassembles, and emits `PreToolUseHookOutput` if and only if at least one line changed. Splitting is on newlines **only** — intra-line `;`, `&&` and `||` chains are already handled correctly by the upstream engine (verified) and must not be re-split.

Guards, first-match-wins:

```text
tool_name != "Bash"                     -> emit nothing, exit 0
command contains "<<"                   -> emit nothing, exit 0   # heredoc body lines are data, not commands; a bare `git status` inside one WOULD be rewritten if fed alone
line is inside an unterminated quote     -> carry through untouched  # a multi-line quoted string is one logical token
line's first word ⊆ EXCLUDE              -> carry through untouched  # D5, ADR 0015
rtk hook check <line> exit 0            -> take rewritten line
ELSE                                    -> keep raw line
no line changed                         -> emit nothing, exit 0     # never emit an updatedInput identical to the input
```

**Exclusion list (D5) — `EXCLUDE`, defined in the script, one entry per line with the ADR reference as a `#` comment.** Minimum contents: any invocation resolving to `tsc`, `prettier`, or `nx` (ADR 0015: output/exit-code disagreement on verification-critical commands). `pnpm exec` forms must be matched, since that is the shape the engine rewrites.

**Registration — `.claude/settings.json` (D3).** One `hooks.PreToolUse` entry, `matcher: "Bash"`, invoking the script by repo-relative path. The user-global `rtk hook claude` hook is **not** removed by this story and does not need to be: the engine is idempotent (`rtk git status` -> `rtk git status`, verified), so a doubled hook cannot produce `rtk rtk`. Worst case both run and the wrapper's superset result stands.

**Measurement instrument — `tools/sdlc-analyser/rtk-coverage.py` (D4, platform-engineer).** Replays a transcript corpus and prints the actual-vs-achievable table reproduced under "Measured loss". Two modes: `--engine` (baseline — models the first-line defect) and `--wrapper <path>` (post-fix — pipes each command through the wrapper). Corpus is a directory of `.jsonl` transcripts, defaulting to this project's, with the count configurable so the same corpus can be replayed before and after.

**Not built:** no change to `plugins/sdlc/**`. Rationale: the alternative remedy — instructing agents to emit one command per Bash call so line 1 is always the eligible one — would multiply Bash tool calls and breach the Epic's "requests per story must not increase" gate. Rejected on that ground alone.

## Validation gates (AC-3, AC-4, AC-5)

### Gate 1 — replay delta (instrument gate, self-confirming: declared)

`tools/sdlc-analyser/rtk-coverage.py` run in both modes over one fixed corpus. Pass: `--wrapper` reports lost rewrites <= 5% of achievable, against the 71.8% baseline.

**What this gate cannot detect (NA-88 D11):** the wrapper and this gate are authored by the same story, so a passing result proves only that the wrapper does what its own author designed. It cannot detect that the rewritten commands still execute correctly, that outputs remain trustworthy, or that any token was actually saved. It is a smoke test. It is reported as one.

**Falsifiability (the D11 mirror):** the gate discriminates — the same instrument returns 71.8% lost against the unwrapped engine and near-0% against the wrapper, so it is capable of both outcomes on the same corpus. A gate that returned the same number either way would be evidence about nothing.

### Gate 2 — independent confirmation on a real story (the binding gate)

`rtk gain`'s `Total commands` counter, sampled immediately before and after one real `/sdlc:auto` story run, alongside that run's Bash tool-call count from its own transcript.

| Property | Why it is independent |
| --- | --- |
| Owned by upstream rtk, not by this repo | Nothing this story ships can write to it |
| Increments only on real process execution | A dry-run, a fixture or a replay cannot move it |
| Corpus is a story nobody constructed for this test | Not a reproduction authored alongside the fix |

Pass: rewrites-per-Bash-call on the post-fix story exceeds the same ratio measured on a named pre-fix story. **Both stories must be named in the PR body** — a single post-fix number proves nothing without its pre-fix pair. Suggested pre-fix reference: NA-88's own implementation run, already complete on develop and measurable from its retained transcript.

Pass: zero rewrites. Rationale: this is the one gate whose failure mode is a silently green merge, so it is checked directly rather than inferred from the token numbers.

## Error Handling

| Scenario | Behaviour |
| --- | --- |
| `rtk` binary absent from `PATH` | Emit nothing, exit 0 — the harness runs the raw command unchanged. A hook must never block a tool call it cannot improve. |
| `rtk hook check` exits non-zero for a reason other than "no rewrite" | Keep the raw line; continue with remaining lines |
| `rtk hook check` hangs | Per-line timeout, 2s; on timeout keep the raw line |
| stdin is not valid JSON | Emit nothing, exit 0 |
| `tool_input.command` missing or empty | Emit nothing, exit 0 |
| Command contains a heredoc (`<<`) | Emit nothing, exit 0 — whole-command passthrough, no partial rewrite |
| Reassembled command differs from input only in whitespace | Emit nothing, exit 0 |
| Wrapper itself throws | Emit nothing, exit 0 — failure is always passthrough, never a blocked or mutated command |

**Offline behaviour:** N/A — no network dependency; `rtk hook check` is local.

## Open Questions

- [ ] Should the user-global `~/.claude/settings.json` `rtk hook claude` entry be removed once the wrapper ships? — **Suggested default: no.** The engine is idempotent so double-firing is harmless, and the file is outside the repo. Document the option in the PR body; leave the decision to the operator.
- [ ] Where should the wrapper live — `.claude/hooks/` (ai-enablement-engineer) or `tools/` (platform-engineer)? — **Suggested default: `.claude/hooks/rtk-line-scan.sh`.** It is runtime AI configuration, not analysis; the measurement script goes to `tools/sdlc-analyser/` alongside `duplicate-reads.py` and `artifact-contract.sh`, matching NA-88's split.
- [ ] Does the first-line defect warrant an ADR? — **Suggested default: yes, but not in this story.** It supersedes nothing, but it materially qualifies ADR 0015's "revisit if the rtk hook is fixed upstream" clause. Route it through `/sdlc:docs seed adr` after the fix lands, so the ADR can cite a measured post-fix result rather than a prediction.
- [ ] Should `EXCLUDE` be sourced from rtk's own `[hooks] exclude_commands` config key instead of hard-coded in the script? — **Suggested default: hard-code in the script.** The config file lives at `~/Library/Application Support/rtk/config.toml`, outside the repo and unversioned, so a repo-owned guard cannot depend on it.
- [ ] How many transcripts should the replay corpus fix at? — **Suggested default: 12**, the corpus used for every number in this spec, so before/after are directly comparable. Make it a flag, not a constant.
